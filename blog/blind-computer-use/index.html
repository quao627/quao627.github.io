Blind Computer Use

Given just a binary, language agents build their own tools for a program and use it better than agents that watch the screen

Published

November 2026

TL;DR

We give a language agent only the compiled binaries of a program and a reverse-engineering toolkit. The agent builds its own tools for the program. With these tools, it uses the program much better than the same model does by operating the screen. In FreeCAD, Kimi K2.6 finished one task 10× faster and with 57× fewer tokens when it used the MCP server it built. Across five tasks it passed 87% of the checks with its MCP server and 33% with computer use. In Fruit Ninja, a closed-source real-time game, DeepSeek V4.1 Flash averaged 295 points with its MCP server and 79 points with computer use.

With computer use, a language agent operates software the way a person does. It looks at screenshots and moves the mouse. This works on any program, but every step needs a new screenshot and a new model reply. Agents work better when a program offers tools that they can call directly, such as an MCP server (Song et al., 2024; Jia et al., 2025). So far, people have written these tools by hand or generated them from source code and documentation. For closed-source software, there is no source code to generate them from.

We ask whether an agent can build these tools itself when it has only the compiled binaries of the program. We give the agent REA, a reverse-engineering toolkit that can inspect binaries and instrument running processes. We do not give it source code, documentation or internet access. The agent studies the program and writes an MCP server for it. After that, the agent does its tasks through only this server, without using the screen, mouse or keyboard. We observed superior performance and call this blind computer use.

How an agent builds an MCP server from binaries

We give one agent session the binaries and REA in an offline sandbox, and ask it to build an MCP server. The agent builds the server in four steps (Figure 1):

  1. Analyze. The agent inspects the package and finds what the binaries expose.
  2. Test. The agent runs the program and tries its guesses on it.
  3. Build. The agent writes the MCP server.
  4. Check. The agent runs the server against the program. If a check fails because of a bug in the code, the agent goes back to step 3 and fixes the code. If the failure raises a new question about the program, the agent goes back to step 2 and tests it.

We do not show the agent the benchmark tasks, so the agent has to decide by itself which operations the server should offer.

What does the agent spend its time on during a build?

GLM-5.3's build for FreeCAD took 18 minutes and 152 tool calls. About two thirds of these calls tested the program. Writing the server took only 7 calls and about 20 seconds. For example, early in the build the agent found that FreeCAD's console program exits immediately if it is not started from a terminal, and it changed the server to start FreeCAD that way.

Each tool that comes out of a build does one whole operation. For example, the server that Kimi K2.6 built has a boolean_cut tool, so cutting a vent into the lid is one call, boolean_cut(name=Vented2, base=Vented1, tool=Vent2). With computer use, the same model worked through FreeCAD's menus and dialogs for 40 minutes and did not cut any vent.

How a tool call reaches FreeCAD

The server lets the agent run FreeCAD's own operations with a tool call. It starts FreeCAD, attaches to it with Frida, and injects a small script into it. When the agent calls a tool, the script calls the matching FreeCAD functions inside the running program, for example to save a document or export a STEP file.

How well do agents work with the MCP servers they built?

After each build finishes, the agent cannot change the server any more. We give the server to the same model, together with five FreeCAD tasks that the agent did not see during the build. Each task has multiple checks on the files the model saves. Each task starts from a project file that already passes a few of them.

Main result

Kimi K2.6 passed 87% of the checks with its MCP server and 33% with computer use

Kimi K2.6 does each task twice, once with its MCP server and once with computer use. With computer use, Kimi completed the shortest task. On the other four tasks, it did not pass any check beyond the ones the starting file already passed. The MCP runs also cost less. The five tasks took 62 minutes and 10.7M tokens with the MCP server, and 142 minutes and 65.8M tokens with computer use. The build is a separate cost that the agent pays once per program, and GLM-5.3's build took 18 minutes.

GLM-5.3 passed every check on all five tasks with the MCP server it built. It finished the longest task in 79 seconds on average.

Ablation

A server that the agent writes without access to the program does not work

FreeCAD's Python API is widely documented, so a model might be able to write the server from memory. To check this, we run the build again, but this time we do not give the agent REA or FreeCAD's files. On the five tasks, GLM-5.3's server did not pass any check beyond the starting file, and Kimi's server passed 27% of the checks. The servers that the same models built with REA passed 100% and 87%. Both servers written from memory failed on the first tool call, before the call reached any FreeCAD API.

In a closed-source, real-time game, the model scores 3.7× higher with its MCP server

FreeCAD is open source, and its tasks have no time pressure. Fruit Ninja is closed source and runs in real time. While the model is thinking, fruit falls off the screen.

We give DeepSeek V4.1 Flash the game's binary and REA, and it builds an MCP server in the same four steps. The same model then plays three 60-second rounds with the server and three rounds with computer use. The model averaged 295.0 points per round with its MCP server and 78.7 points with computer use. Most of the computer-use score is a bonus that the game adds when a round ends. In the round shown in Demo 2, the model earned 9 points during play with computer use and 288 points with its MCP server.

The server's game_state tool reads the score, the clock, and the fruit and bombs from the game process. Its slice tool plans one stroke through the fruit and performs it. The model does not need to find the fruit in an image.

Why an agent does not need the screen

In this part, we share some of our interpretation of what we see in the results.

A skilled user knows which operations to do without studying the screen

An experienced FreeCAD user does not need to analyze the screen to know what to do next. To cut a vent into a lid, they already know the operations: make a box, place it, and subtract it from the lid. In the GOMS model of skilled computer use, an expert knows goals and the methods that reach them, and clicks and keystrokes are only how the methods get carried out (Card, Moran and Newell, 1983). Blind people use software through a screen reader that reads the names of the buttons and menus aloud. Experienced users often write scripts instead of clicking.

A model works with a tool call more cheaply than with a screenshot

The same information can be easy or hard to use depending on how it is presented. A person reads a diagram faster than a paragraph that says the same thing (Larkin and Simon, 1987). A language model is the opposite, and works with text more cheaply than with images. The call add_box(length=40, width=3, height=7) and a screenshot of the lid describe the same step. With the screenshot, the model has to find the right field, work out where to click, and read the result from another screenshot. On lid-vent, computer use spent 17.2M tokens and the MCP run spent 0.3M.

An agent can play with the software before it has a task

In our setting, the agent gets time to play with the program before it receives any task. It starts the program, tries things to see what happens, and learns what the program can do. About two thirds of the calls in GLM-5.3's build were like this. They added nothing to the server and only showed the agent how the program behaves. A Tetris player does something similar when they rotate a piece just to see where it fits (Kirsh and Maglio, 1994). After that, the agent turns what it learned into tools, so it is ready for tasks it has not seen yet.

How this relates to prior work

Earlier work shows that agents do better with APIs or MCP tools than with only the screen. This has been shown on the web (Song et al.), in IDEs (Aggarwal and Welleck) and on the desktop (UFO2, CoAct-1, OSWorld-MCP, MCPWorld). We ask a different question: where do the tools come from when nobody has written them?

Agents can already analyze binaries with tools such as GhidraMCP, ida-pro-mcp and LLM4Decompile. We do not know of earlier work where the agent turns this analysis into a tool server and then does a user's tasks through the server.

Next: let agents shape their own link to the environment

In our experiments, the agent builds the server only once, before it sees any task. After it starts to receive tasks, it does not update the server. But the agent still has the program, and it can go back to it at any time.

The next step is to let the agent keep changing the server while it does tasks (Figure 9). The server is the agent's link to the software, and the agent built this link itself. So the agent can also decide what the link should look like. When a task is awkward with the current tools, the agent can go back to the binary and test how that part of the program behaves. Then it can add a tool, redesign a tool, or combine several steps into one tool. In Fruit Ninja, the agent already chose to build one slice tool that plans a whole stroke and performs it. Over time, the agent defines how it wants to work with the software, and the link evolves with the tasks it does. An MCP server built this way can also be shared with other agents.

If this works, a program does not need to ship an agent interface for agents to use it well. An agent starts with only the installed program, designs for itself how to work with it, and gets better at using it over time. Software is one kind of environment. We are excited about agents that shape their own links to the environments they work in, starting with the software on a computer.
